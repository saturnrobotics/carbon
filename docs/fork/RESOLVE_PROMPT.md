# Resolve upstream merge conflicts on a sync branch

You are resolving the conflicts of a merge of `upstream/main` (crbnos/carbon) into
this fork's trunk `saturn/main`. You are on a `sync/upstream-*` branch and the merge
is open in this checkout: `git status` shows unmerged paths and `MERGE_HEAD` is set.
If instead the branch's last commit is `WIP: unresolved upstream conflicts`, re-open
the merge first:

```bash
git reset --hard "$(git merge-base HEAD origin/saturn/main)"
git merge --no-ff --no-commit upstream/main
```

## Direction of intent

- For **shared code** (any file that exists in `upstream/main`), upstream is the
  intended direction. Take upstream's structure and behaviour; re-apply the fork's
  change on top of it only where the fork deliberately customizes that file.
- For **fork-owned code**, the fork is the intended direction. What the fork
  deliberately customizes is documented in `docs/fork/CUSTOMIZATIONS.md`; read it
  before deciding, and read `docs/fork/CONVENTIONS.md` for where fork code belongs.
- When both sides changed the same lines for **orthogonal** reasons (upstream
  fixed a bug, the fork added a hook; upstream renamed a variable, the fork added a
  field), keep both behaviours.
- When they are **not** orthogonal — the two sides want different behaviour from
  the same code, a fork feature depends on something upstream removed, an upstream
  change makes a fork customization redundant or wrong — do **not** guess. Stop,
  leave that file conflicted, and describe the semantic conflict in a PR comment:
  what upstream intends, what the fork intends, and the options you see.

## Scope

- Resolve **only** the files that currently carry conflict markers
  (`git diff --name-only --diff-filter=U`). Do not edit, reformat, or "improve"
  any other file, even if you notice a problem; mention it in your summary instead.
- Never resolve a `merge=regen` file by hand (check with
  `git check-attr merge <path>`): database types, swagger schema, backup manifest,
  MCP tool digest, workflow catalog, agent knowledge base, `pnpm-lock.yaml`,
  `Cargo.lock`. They are regenerated by `bash scripts/fork/regenerate.sh`, which
  the finish script runs for you. If one of them shows as conflicted, the driver
  was not configured: run `bash scripts/fork/setup-git.sh` and re-open the merge.
- Do not change migrations that already exist on either side. If both sides added
  a migration with the same version number, rename the fork's (new timestamp,
  `saturn-` slug) and say so.
- Do not touch `.github/workflows/`, `scripts/fork/`, `.gitattributes`, or
  `docs/fork/` unless they are themselves conflicted; a conflict there is a
  semantic conflict to report, not to resolve.

## Procedure

1. `git status` and `git diff --diff-filter=U` to see every conflicted hunk with
   `zdiff3` markers (the `|||||||` section is the common ancestor).
2. For each file: read the ancestor, ours and theirs versions
   (`git show :1:<path>`, `:2:<path>`, `:3:<path>`), decide per the rules above,
   write the resolution, remove all markers, and `git add <path>`.
3. When every file you are allowed to resolve is staged, run
   `bash scripts/fork/finish-sync.sh`. It verifies that no markers remain,
   regenerates the generated files, runs the migration-ordering guard and commits.
4. Run the checks: `pnpm exec biome check`, `pnpm run typegen && pnpm run typecheck`,
   `pnpm test`. Fix failures that your resolution caused; report the rest.
5. Post a summary comment on the PR with one line per conflicted file:
   `path — resolution — one-line rationale`, followed by any semantic conflicts you
   left open and any check failures you could not attribute to the merge.

You are done when `finish-sync.sh` has committed, the checks have run, and the
summary comment is posted. If you had to stop on a semantic conflict, leave the
merge in progress, do not commit, and make the comment your final action.
